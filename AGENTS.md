# Agent guide

Rules for coding agents (Claude Code, Cursor, Copilot, Codex and others) working in this repo. Human teammates follow the same git workflow.

Before writing code, read [README.md](README.md) for the overview and [docs/mvp.md](docs/mvp.md) for the spec. The reasoning behind both is in [docs/alumni-path-map.md](docs/alumni-path-map.md). Before any front-end work, also read [DESIGN.md](DESIGN.md), which sets the visual theme.

## Git workflow

1. Never commit or push to `main`. All work reaches `main` through a pull request.
2. Start from current `main`: `git switch main`, `git pull`, then `git switch -c <area>/<short-topic>`. Examples: `engine/lift-query`, `map/goal-box`, `events/engage-parser`.
3. Keep one topic per branch and make small commits whose messages say what changed.
4. Before pushing, bring current `main` into the branch and run what you changed.
5. Push the branch with `git push -u origin <branch>` and open a pull request into `main`. Use `gh pr create` if it is installed. If it is not, give your human the compare link that `git push` prints.
6. Do not merge the pull request. A human teammate merges it.
7. Never force-push, never rewrite history on a branch someone else uses, and never delete a branch you did not create.

In the pull request description, say what changed, how you checked it, and what is not done or not tested.

## Stay in your lane

Five people work in parallel and each role owns a folder (see the table in [docs/mvp.md](docs/mvp.md#repo-layout)). Edit only the folders of the role you are working for. If the task needs a change in someone else's folder, stop at the boundary, say so in the pull request or to your human, and let that folder's owner make the change. This is what keeps five parallel branches free of merge conflicts.

## The API contract

The JSON shapes in [docs/mvp.md](docs/mvp.md#api-contract) are the interface between the backend and the front end, and both front-end people build against fake data in those shapes. Do not change a shape silently. If one has to change, update `docs/mvp.md` in the same pull request and say so at the top of the description.

## Product rules

- **This is a path map, not a feed and not a chatbot.** Do not add posts, likes, chat, a general events list or a conversational interface.
- **The LLM does two things:** it parses the goal and it drafts the ask. Stops and rankings come from counting in SQL. Do not move that logic into a prompt.
- **Score stops by lift, not raw count.** An activity that everyone does must drop out of the map.
- **Show counts, not causes.** Interface text says "9 of 14 did this" and never claims that a stop gets you the goal.
- **People are seeded.** Every person in the database is generated by the seed script. Do not scrape LinkedIn or import real personal data. Events are the one exception: they are real public listings.
- **The demo comes first.** `main` must always run the demo as far as it has been built. Follow the build order in the README, and do not start a later step in a way that breaks an earlier one.
- **Stay inside the MVP.** Do not build login, chat, a general events feed, real data import or a mobile layout, even if it looks quick.

## Code rules

- Keep secrets out of the repo. API keys go in `.env`, which is ignored by git, and their names go in `.env.example`.
- Every LLM call needs the offline fallback described in [docs/mvp.md](docs/mvp.md#llm-use), so that the demo survives a bad network or a missing key.
- Make the smallest change that does the job. Do not add a dependency, framework or abstraction the task does not need, and ask your human before adding a large one.
- Run your change before opening the pull request, and report honestly what you ran and what you did not.
- WarmPath is the product name and SWARM is the repo name. Use WarmPath in anything a user sees.
